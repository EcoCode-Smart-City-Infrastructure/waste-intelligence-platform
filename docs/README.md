# Waste Intelligence — Web App

Zero-build static web app for the EcoCode Waste Intelligence Platform, published by GitHub Pages from branch `web-app`, folder `docs/`.

## Views
- **Dashboard** — demo fleet KPIs, urgent bins, live DSNY tonnage aggregated by borough.
- **Live NYC Data** — direct Socrata queries: `ebb7-mvp5` (tonnage), `gaq9-z3hz` (diversion/capture), `6yag-pnij` (organics), `6r9j-qrwz` (facilities). Labelled sample fallback only if the live call fails.
- **Bins & Routes** — demo fleet (hub API returns no bins), add/collect bins, nearest-neighbour collection route, localStorage persistence.
- **Forecasting** — ports `services/forecasting/app.py`: current-cycle cut on a drop > 30 points, least-squares slope, R², time-to-full, z-score anomaly.
- **Knowledge Graph** — the repo's real sample: `cloud_platform/analytics/kg/data/w2rkg_nyc_sample.json` (31 nodes, 55 edges), in `kg.json`.
- **Contamination** — backend acceptance map from `services/contamination/app.py`, with manual material tagging. YOLOv11 itself needs the backend service and cannot run on Pages.
- **Connect** — probes a locally running hub / forecasting / contamination service at `/health`.
- **Kepler 3D Map** (`kepler.html`, real Kepler.gl 3.0.0 loaded from unpkg, no build step) — geospatial operations view over the same data: demo fleet points coloured/sized by fill, a 3D fill-density grid, urgent-route arcs, live tonnage-by-borough points, and 48-hour fill tracking with a time-range filter. Kepler's own side panel provides layer switching, filters, split maps, drag-and-drop CSV/GeoJSON, and config/image export. Presets (Fleet 3D / Routes / Tonnage / Tracking) move the camera and switch layers through Kepler actions. Default basemap is CARTO Dark Matter (supplied to Kepler as a custom style, no token). Kepler's Dark/Light/Muted/Satellite styles are mapbox:// URLs and show a blank canvas without a token; a Mapbox token can be pasted on the page (stored in that browser's localStorage only) to unlock them. The knowledge graph is deliberately not geo-plotted — its nodes have no coordinates.

## Knowledge Graph loops — every element, plus the assistant protocol

- **Demonstration loop for every element**: the Knowledge Graph view has a gallery of all 31 nodes. Each element's loop is a staged journey Waste → Process → Resource → Demand (Actor) → Facility → back to Waste, built from real sample edges where they exist.
- **Honest cycle note**: no node in the 31-node sample sits on a directed cycle, because the sample's demand actors (Urban Farm, Waste Processor, NYC Urban Agriculture) do not operate facilities. Every loop therefore has four real steps plus one dashed, labelled bridge (demand → facility, or facility → next load). Bridges are system steps, never presented as sample edges. Constraints (Local Law 146, Odor Control, Heavy Metal Limits) do not form loops on their own; they are shown as gates on the loop of the element they apply to.
- **Ask for a loop (in the page)**: the “Ask for a loop” field parses plain language against the sample. Two matched elements with a directed sample path animate that path; one matched element plays its loop; nothing matched produces a plain “not in the sample” result plus a Loop Studio draft — never an invented pathway.
- **Loop Studio (in the page)**: build a loop from existing nodes, save it in that browser's localStorage, export it as JSON, or import pasted JSON. Saved loops appear under “Your loops” and play in the same loop player.
- **Curated loops (`loops.json`)**: the app loads `docs/loops.json` if present and lists those loops under “Your loops” with a “curated” badge. Format, one object per loop:
  ```json
  {"name": "Brooklyn Residential Organics Loop", "desc": "...", "source": "curated-sample", "stages": ["ResidentialOrganicsBrooklyn", "AerobicComposting", "CompostAmendment", "UrbanFarm", "FACILITY-BK-COMPOST-01"]}
  ```
  Stages are node IDs from `kg.json`, in Waste → Process → Resource → Actor → Facility order. Transitions between consecutive stages are computed from `kg.json` edges at render time; a missing edge is rendered as a labelled bridge.
- **Ask Muse in chat (the AI research step)**: the static Pages app runs no AI model. To get a researched loop, tell Muse in chat, for example: “Add a W2RKG loop to the waste web app (branch web-app, docs/loops.json): coffee grounds to animal feed.” Muse should use the sample first, then research real conversion data with labelled sources, never invent metrics, add the loop to `loops.json`, and push it — it then appears in “Your loops” on the next visit. The in-app “Copy request for Muse” button copies exactly that request template with your words filled in.

## Embedded AI assistant (Assistant view)

Mirrors the platform's `copilot_service/` (prompt builder, context manager, tool router, guardrails) and Project ATMA's streaming chat, adapted to a static Pages app.

- **Live chat — Groq direct (most effective for Pages):** paste your own Groq key in the Assistant view's Connect card. It lives only in that browser's localStorage and is sent only to `https://api.groq.com/openai/v1/chat/completions`, streaming (SSE), with last 50 messages kept locally and last 10 sent as context. Models: `llama-3.3-70b-versatile` (default) and `llama-3.1-8b-instant`. A “Test key” button calls only the models endpoint and reports status/count, never the key.
- **Demo mode (no key):** answers from a built-in knowledge base in the page — fleet summary, knowledge-graph loops, contamination map, forecasting method, live-data sources — labelled as demo.
- **Repo-secret backend — Actions briefing only (GROQ_API, for now):** a repo secret cannot power live chat on a static site, because the browser can never read it and any key shipped in the bundle would be public. Its one legitimate use here is the briefing card, and a secret in one repo cannot be read by another repo's workflow — so the OpenForge route is: copy `github-workflows/groq-waste-briefing-openforge.yml` by hand to `.github/workflows/groq-waste-briefing.yml` in `Etienne0101-lab/OpenForge-Workbench-` (the GitHub App cannot create workflow files) and dispatch it there. Inside that runner only, it reads `${{ secrets.GROQ_API }}` (the secret Stephen installed in the OpenForge repo — never paste the value), fetches the latest public DSNY tonnage, asks Groq for a short briefing, and commits only `docs/waste-ai-briefing.json` to OpenForge Pages, which the Assistant view fetches (newest briefing wins) alongside this repo's own `docs/ai-briefing.json`. Alternative: add a `GROQ_API` secret to this waste repo and run `github-workflows/groq-briefing.yml` here instead. The key is never printed or committed.
- **Platform backend (copilot_service):** Groq is now the preferred provider when `GROQ_API` (or `GROQ_API_KEY`) is set as an environment variable where the service runs — see `copilot_service/utils/groq_client.py` and `docker-compose.yml` (set `GROQ_API` in `.env`). OpenRouter remains the fallback when no Groq key is set. A repo secret alone does not run the platform service; it only enters via Actions or via `.env` on the host.
- **Guardrails:** the assistant is read-only. It will not delete or modify bins, change routes, actuate anything, or reveal a key/secret value. It explains and links to the view where you make the change yourself. This mirrors `copilot_service`'s forbidden actions (route/actuate/write/delete) and sensitive-field handling.
- **Limited troubleshooting (Diagnose & repair card, Assistant view):** say "diagnose the app" in chat, or press Run diagnostics. Diagnostics are read-only and check Socrata feeds (ebb7-mvp5, gaq9-z3hz, 6yag-pnij, 6r9j-qrwz), kg.json / loops.json, both briefing sources, saved local data (fleet, readings, custom loops, assistant history), Groq-key presence only, and any Connect backend URLs entered this session. Repairs are click-to-apply and local to that browser only: retry live feeds, reload graph + loops, re-probe Connect backends, reset the demo fleet, clear custom loops, clear assistant history, clear all saved app data (Groq key kept), reload the page. Destructive repairs confirm first; no repair runs from a chat message alone, and a troubleshooting chat message runs diagnostics and summarises them instead of calling the model. This card cannot fix a Pages deployment, a repo secret, an Actions workflow, or a server that is actually down — in those cases it names the exact next step.
- **Optional shared-key proxy (not built by default):** if you later want visitors to chat without pasting their own key, the correct route is a tiny serverless proxy (Cloudflare Worker / Vercel Function) holding the Groq key as *its own* secret with rate limiting — not a repo secret, and not in this repo. Say the word and that is a separate, small deployment.

## Dashboard (dark operations layout, 2026-10-25)

The Dashboard view is a dark sidebar + card-grid layout (sidebar: Operations / Intelligence / Account; top strip: search, urgent bell, settings, sign-in), populated only with waste data: fleet fill by borough, live tonnage total + waveform bars, tonnage-mix donut, fill heatmap, ring gauges (healthy bins, live feed, organics share), urgent bins, tonnage by borough, forecast trend for the most urgent bin, the loop example, and the live tonnage table. The layout and card structure follow the reference dashboard Stephen supplied; labels, numbers, and artwork are original to this app — no template text, emblem, or screenshot numbers were copied.

At the top sits the **City grid — live operations**: a 2D interactive SVG grid (not a 3D rendering, not a phased loop) with animated data pulses along the urgent route, bin dots sized/coloured by fill, layer toggles (Fleet / Urgent route / Fill heat / Borough labels), a Pause/Resume pulses button, and tap-a-bin-dot navigation to Forecasting. The Kepler Map remains a separate view; the dashboard itself no longer depends on 3D.

## Run locally
```bash
python3 -m http.server 8000   # then open http://localhost:8000/
```
No build step, no API key.

## Sign-in (login.html)
- **Email accounts**: fully working in-browser. Create an account on `login.html` (name, email, password ≥ 8 chars); the password is stored only as a SHA-256 hash in `localStorage` (`wi-accounts-v1`), the session in `sessionStorage`. Accounts do not travel between devices and no verification email is sent — demo-grade local auth, not a server account system. Do not reuse a real password.
- **Google / Apple**: wired to their real client SDKs in `auth.js`, gated by `auth-config.js`. With no client ID configured (the shipped state) the buttons open a setup panel instead of faking a sign-in. Add a Google OAuth client ID / Apple Service ID for the Pages origin to enable them; for shared, server-verified accounts, replace the local store with Firebase Auth, Auth0, or Supabase.
- The app header shows the signed-in account and a Sign out link; signing in is optional — the demo remains open to guests.
